# botyara

Локальное клиент-серверное приложение на Python для постановки задач и получения
результатов через HTTP. Сервер предоставляет веб-панель и API, хранит данные
в SQLite. Клиент поддерживает команды `whoami`, `ip` и `exit`.

Протокол общения настраивается отдельно для каждого payload: HTTP-метод,
формат передачи и имя поля. Каждый запуск клиента получает собственный callback
с отдельной очередью задач.

## Требования и установка

Windows 10 или 11, Python 3.10 или новее, PowerShell.
Зависимости: Flask, Requests и psutil; диапазоны версий указаны в requirements.txt.

Выполните в корне проекта:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

## Запуск

В первом терминале запустите сервер:

```powershell
.\.venv\Scripts\python.exe .\server.py
```

Во втором терминале запустите клиента:

```powershell
.\.venv\Scripts\python.exe .\client.py
```

Веб-панель доступна по адресу **http://127.0.0.1:5000/**. Выберите активный
callback, команду и нажмите «Отправить». Результат появляется после следующего
опроса сервера клиентом; для обновления панели нажмите «Обновить».

Для запуска двойным щелчком доступны:

| Файл | Назначение |
|---|---|
| server.cmd | Сервер |
| client.cmd | Клиент с настройками текущего окружения |
| clientstandart.cmd | Клиент с профилем standard |
| clientmixed.cmd | Клиент с профилем mixed |

Скрипты используют Python из .venv и переходят в каталог проекта.
Скрипты для конкретных профилей сбрасывают BOT_CONFIG только в окружении своего
запуска, чтобы использовать отдельные стандартные файлы конфигурации.
Сначала запустите сервер, затем нужные клиенты.

Для остановки процесса используйте Ctrl+C. Команда exit завершает выбранного
клиента после отправки результата.

## Конфигурация

Настройки читаются из переменных окружения при запуске процесса.

| Переменная | По умолчанию | Назначение |
|---|---|---|
| BOT_SERVER | http://127.0.0.1:5000 | Адрес сервера для клиента |
| BOT_PORT | 5000 | Порт сервера |
| BOT_DATABASE | server.db рядом с database.py | Путь к SQLite |
| BOT_PROFILE | standard | Профиль для создания нового конфига: standard или mixed |
| BOT_CONFIG | `payload-<профиль>.json` рядом с client.py | Путь к конфигу клиента |
| BOT_SLEEP | 5 | Базовая пауза между циклами опроса, секунды |
| BOT_JITTER | 0.3 | Случайное отклонение от паузы, доля единицы |

Пример запуска mixed с паузой от 6,4 до 9,6 секунды:

```powershell
$env:BOT_PROFILE = "mixed"
$env:BOT_SLEEP = "8"
$env:BOT_JITTER = "0.2"
Remove-Item Env:BOT_CONFIG -ErrorAction SilentlyContinue
.\.venv\Scripts\python.exe .\client.py
```

Sleep задаётся положительным числом, jitter — числом от 0 до 1.
Дробная часть отделяется точкой. Jitter ограничивается диапазоном 0–1,
минимальная пауза составляет 0,1 секунды. Время запросов и выполнения задачи
прибавляется к паузе. Фактическое значение выводится в консоль.

### Конфиг клиента

Если файл отсутствует, клиент получает payload UUID и профиль через POST /payloads
и сохраняет их вместе с server_url в JSON-файл UTF-8 без BOM.
Если файл существует, клиент использует его повторно. BOT_SERVER должен
совпадать с сохранённым адресом.

Несколько запусков с одним конфигом используют общий payload, но получают разные
callback UUID. При первом создании общего конфига дождитесь сохранения файла
одним клиентом, прежде чем запускать следующий.

Для отдельного payload того же типа задайте новый путь:

```powershell
$env:BOT_CONFIG = "payload-second.json"
.\.venv\Scripts\python.exe .\client.py
```

BOT_PROFILE не изменяет профиль уже сохранённого конфига. Для другой базы
или другого сервера используйте отдельный файл. BOT_PAYLOAD не используется.

## Профили HTTP

Встроенные профили определены в profiles.py:

| Операция | Адрес | standard: метод / transport / поле | mixed: метод / transport / поле |
|---|---|---|---|
| checkin | /checkin | POST / json / payload_uuid | GET / query / id |
| get_task | /poll | POST / json / callback_uuid | POST / form / cb |
| post_task | /results | POST / json / data | POST / form / data |

Transport json передаёт данные в JSON-теле, form — в теле
application/x-www-form-urlencoded, query — в параметрах URL.
Поддерживаются методы GET и POST; GET допускается только с query.

Каждый рабочий запрос содержит заголовок X-Payload-UUID. По нему сервер находит
сохранённый профиль и определяет, откуда читать данные. UUID регистрации должен
совпадать со значением заголовка; callback и задача должны принадлежать
соответствующему payload и клиенту.

Для регистрации и опроса значение поля — строка UUID. Для результата — объект
с callback_uuid, task_id и result. В JSON объект передаётся напрямую,
а в form/query предварительно преобразуется в JSON-строку.

## HTTP API

| Метод и адрес | Назначение |
|---|---|
| GET /ping | Проверка доступности |
| POST /payloads | Создание payload и выдача профиля |
| GET/POST /checkin | Регистрация callback; метод по профилю |
| GET/POST /poll | Получение задачи; метод по профилю |
| GET/POST /results | Отправка результата; метод по профилю |
| POST /tasks | Создание задачи через JSON |
| `GET /tasks/<callback_uuid>` | Просмотр следующей задачи без её выдачи |
| GET /state | Состояние payload, callback и задач |
| GET / | Веб-панель |

### Создание payload

POST /payloads принимает JSON с именем встроенного профиля:

```json
{"profile":"mixed"}
```

Пустой объект выбирает standard. Вместо имени можно передать полный объект
с правилами checkin, get_task и post_task. Каждое правило содержит method,
transport и непустое строковое field длиной до 64 символов.
Ответ с кодом 201 содержит payload_uuid и полный profile.
Каждый вызов создаёт новый payload; профиль сохраняется в базе как отдельная копия.

### Задачи и результаты

POST /tasks принимает JSON:

```json
{"callback_uuid":"<callback UUID>","command":"whoami"}
```

Ответ с кодом 201 содержит task_id и статус pending.
Опрос /poll возвращает {"task":null}, если очередь пуста, либо объект:

```json
{"task":{"task_id":1,"command":"whoami"}}
```

Для профиля standard тело запроса /results выглядит так:

```json
{"data":{"callback_uuid":"<callback UUID>","task_id":1,"result":"..."}}
```

После выдачи задача имеет статус sent, после сохранения результата — completed.
Повторная отправка того же результата допустима; замена уже сохранённого результата
отклоняется. Ответ об успешном сохранении: {"status":"completed"}.

## Хранение и ограничения

База SQLite создаётся при первом запуске сервера. init_db обновляет схему
существующей базы, сохраняя историю; payload без профиля получают standard.
Клиенты без заголовка X-Payload-UUID и обёртки поля результата несовместимы
с текущим протоколом.

- Сервер слушает только 127.0.0.1; приложение предназначено для локального использования.
- Payload UUID не заменяет аутентификацию.
- Callback считается активным в течение 15 секунд после последнего запроса.
  Новые задачи принимаются только для активных callback.
- Результат ограничен 20 000 символами, тело запроса — 65 536 байтами.
  Кодирование может увеличить объём: действуют оба ограничения.
- Длина URL ограничена HTTP-сервером; query подходит для коротких данных.
- /poll обновляет состояние даже при выборе GET в профиле. Ответы API не кэшируются.
- Доступны только whoami, ip и exit; произвольные команды не поддерживаются.

## Устранение неполадок

| Проблема | Действие |
|---|---|
| Не найдена .venv | Выполните установку из корня проекта |
| Порт занят | Остановите прежний сервер или измените BOT_PORT и BOT_SERVER |
| Payload не найден | Проверьте базу сервера; для новой базы используйте новый BOT_CONFIG |
| В конфиге другой сервер | Согласуйте BOT_SERVER с конфигом или выберите новый файл |
| Нет активного callback | Проверьте процесс клиента, обновите панель и сопоставьте UUID |
| Задача остаётся в очереди | Проверьте, что она назначена текущему callback, а не прежнему запуску |

## Структура проекта

- server.py — HTTP API и веб-панель;
- client.py — конфигурация клиента, запросы и выполнение задач;
- database.py — схема SQLite и операции с данными;
- profiles.py — встроенные профили и их проверка;
- templates/, static/ — интерфейс панели;
- requirements.txt — зависимости.
